# 開発の経緯

kanaterm は動作する初版を作ったあと、リファクタリングとデバッグの工程で複数の不具合と設計上の判断ミスが見つかっている。同じ罠を再び踏まないよう、見つかった問題とその原因、採用しなかった案を記録する。

## 初版の構造とリファクタリング（2026-09-05）

初版は `main.js`（433行）と `renderer.js`（483行）の2ファイルに全処理が入っていた。動作はしていたが、次の問題があった。

- **プリセットの二重定義** — 配色6種とタブ色7種が、`main.js`（右クリックメニューの選択肢）と `renderer.js`（実際の描画色）に別々に書かれていた。片方だけ直すと「メニューには出るが色が付かない」というずれが起きる状態だった。
- **永続化・メニュー定義・ウィンドウ管理が一箇所に混在** していた。

以下に分割した。

| ファイル | 役割 |
| --- | --- |
| `presets.js` | 配色・タブ色・フォントサイズ（main / renderer 共用） |
| `store.js` | `state.json` とスクロールバックの読み書き |
| `menus.js` | 右クリックメニューの定義 |
| `logger.js` | ファイルログ（後述） |

### renderer 側をESモジュールにしなかった理由

`renderer.js` も分割候補だったが、Electron は `loadFile()` でページを `file://` として読み込む。Chromium は `file://` の ES モジュールを CORS で拒否するため、`import` は使えない。カスタムプロトコルを登録する手もあるが、この規模には見合わないと判断した。

共用したいのはプリセットだけだったので、`presets.js` の末尾で `typeof module` を見て CommonJS / クラシックスクリプトの双方から読めるようにし、renderer 側はグローバル `PRESETS` を参照する形にした。`renderer.js` は1ファイルのまま、区分けのコメントで整理するにとどめた。

## 見つかった不具合（2026-09-05）

### 1. Ctrl+Shift+I（DevTools）が何も起きない

`webContents` の `before-input-event` は keyDown と keyUp の**両方**で発火する。`toggleDevTools()` を無条件に呼んでいたため、開いた直後に閉じており、結果として何も起きないように見えていた。`input.type !== 'keyDown'` で除外して解決。

### 2. 並べ替え後の Ctrl+Tab が見た目と違う順で回る

タブの並べ替えは DOM 要素を動かして表現しているが、タブ切り替えは `Map` の列挙順（＝生成順）を見ていた。並べ替えると両者がずれる。順序の判断は必ず DOM を正とする `tabIdsInOrder()` を通すようにした。タブを閉じた後の移動先も同様に「見えている隣」へ修正した。

### 3. 起動のたびにウィンドウが縦に伸びる

後述の「ウィンドウサイズの丸め」を参照。

### 4. `shell-integration.ps1` が Windows PowerShell 5.1 で構文エラーになる

BOM の無い UTF-8 で保存していたため、Windows PowerShell 5.1 がシステムのコードページ（日本語環境では CP932）として読み、日本語コメントが壊れて構文解析に失敗していた。**`.ps1` は UTF-8 BOM 付きで保存する**必要がある。

### 5. 日本語出力の文字化け

xterm.js は入出力を UTF-8 として解釈するが、Windows PowerShell の既定はコンソールのコードページである。シェル統合スクリプトで `[Console]::OutputEncoding` / `InputEncoding` を UTF-8 に揃えて解決した。

### 6. 空白・`#`・日本語を含むパスで cwd 追従が壊れる

シェル統合が OSC 7 の URI を未エスケープで送出していた。パスのセグメントごとに `[uri]::EscapeDataString` を適用するよう変更。エスケープ結果は ASCII のみになるため、端末側の文字コードにも左右されなくなった。あわせて UNC パス（`\\server\share`）を `file://server/share` として往復できるようにした。

### 7. 存在しないドライブを保存しているとタブが開けない

外付けドライブやネットワークドライブの切断後は、保存された cwd が存在しない。その状態で `pty.spawn` すると例外になる。`resolveCwd()` で存在確認をしてホームへ退避し、`spawn` 自体も try/catch でタブ単位に閉じ込めた（1タブの失敗で他のタブを巻き込まないため）。

### 8. タブを閉じた直後に例外が出る

スクロールバック復元のタイマーが動いたまま `term.dispose()` していたため、破棄済みの Terminal へ書き込んでいた。破棄前に `clearTimeout` するよう修正。

### 9. 終了直前の変更が失われる（最も影響が大きい）

タブ名の変更・色の変更・並べ替えは 500ms の遅延保存に載る。その間に終了すると失われるため、閉じる時に確定させる処理を入れた。

ここで**二段階の思い違い**をしている。

1. 当初は `BrowserWindow` の `close` イベントで確定させた。検証では保存されており、直ったと判断した。
2. しかし後日ログを仕込んだところ、`close` のログが一度も出ていないことに気づいた。**レンダラー発の `window.close()` では `close` イベントが発火しない**（このElectronの挙動）。そして最後のタブを閉じる操作（`Ctrl+Shift+W`・×ボタン・右クリック「閉じる」）は、すべてこの経路を通る。
3. 実際には `closed` が先に走って内部状態を凍結し、後続の `before-quit` の保存が空振りしていた。1で「保存されていた」のは、たまたま遅延保存のタイマーが先に発火していただけだった。

確定処理を `closed` へ移し、**凍結より前に**保存するよう修正した。「変更した直後に閉じる」手順で再現・修正・再検証している。検証手順が甘いと直ったと誤認する典型例だった。

### 10. 終了時のスクロールバックを取りこぼす

`beforeunload` から非同期 IPC で送っていたため、ウィンドウ破棄に間に合わないことがあった。この経路だけ同期 IPC（`sendSync`）にして、書き終えてから閉じることを保証した。

### 11. ページ再読み込みで画面が空になる

二重シード防止のフラグにより、再読み込み時にタブの UI が作り直されず、PTY だけが生きた空のウィンドウになっていた。既存タブがある場合は UI を作り直して繋ぎ直すようにした。

### その他

- 次回起動時に必ず**最後の**タブがアクティブになっていた（アクティブタブを記録していなかった）→ `state.json` に `activeTabId` を追加
- 異常終了で取り残されたスクロールバックが溜まり続けていた → 起動時に `state.json` に無いものを削除
- 右クリックでも「選択と同時にコピー」が動き、選択内容が意図せず上書きされていた → 左ボタンのみに限定
- シェルが終了したタブが生きているように見えていた → タブに取り消し線を付け、死んだ PTY への書き込みを遮断

## ウィンドウサイズの丸め（2026-09-05）

「起動のたびにウィンドウが数pxずつ縦に伸びる」問題は、方式を三度変えている。原因は、拡大率125%の環境で論理座標が整数のデバイスピクセルに乗らず、`setBounds()` した値と `getBounds()` の戻り値が数pxずれることにある。

### 1. コンストラクタに渡す（初版・不採用）

`new BrowserWindow({...bounds})` で復元し、保存時に `getBounds()` を読む方式。実測で「980を渡して983が返る」ことを確認した。保存と復元を繰り返すたびに育つ。

### 2. 生成後に `setBounds()` で入れ直す（改善したが不十分）

`setBounds()` は `getBounds()` と往復が一致する（980を入れて980が返る）ことを確認し、これで解決したと判断した。実際、当初の検証では3回連続で値が変わらなかった。

しかしこれは**たまたま丸めが起きない座標だった**だけだった。座標が変わると再び1〜2pxのずれが出る（例: 1102×682 → 1103×684）。ずれは一度で収束し無制限には育たないが、ゼロではない。

### 3. `moved` / `resized` の時だけ記録する（不採用）

保存のたびに `getBounds()` を読むのをやめ、「利用者が動かし終えた時」だけ控える方式。丸めは完全に消えたが、検証したところ**プログラム由来のサイズ変更では `resized` が発火しない**ことが判明した。OS のスナップや最大化を取りこぼすため不採用とした。

### 4. すべての変化を見るが、自分で適用した分の丸めは無視する（採用・現行方式）

`resize` / `move`（あらゆる変化で発火する）を監視しつつ、自分が `setBounds()` した直後の実測値とほぼ同じ（許容差4px）なら「適用結果の丸め」とみなして無視する。数px単位のリサイズを意図して行うことはないため実害はない。

検証結果:

- 何もせず起動→終了を4回 → 値が1bitも変化しない
- ウィンドウをリサイズ → 正しく記録される（DPI換算も正しい）
- その値のまま起動→終了を3回 → 変化しない

## 機能追加（2026-09-05）

### Ctrl+V での貼り付け

当初は右クリックメニューからのみ貼り付けできた。実装にあたり、貼り付け処理をレンダラー側（xterm.js の `term.paste()`）に集約した。改行の正規化（CRLF → CR）とブラケットペーストの付与を端末の状態に応じて処理してくれるうえ、結果が通常入力と同じ `onData` を通るため、PTY への送信も復元内容の保護解除も既存の経路に乗る。副産物として、main 側が持っていた保護解除用の IPC チャネルが不要になった。

この作業中に、**xterm.js は `defaultPrevented` を見ずにキーを PTY へ送る**ことが分かった。既存のショートカットは `preventDefault()` しか呼んでおらず、`Ctrl+Tab` を押すとタブ切り替えと同時に TAB 文字がシェルへ流れていた。キャプチャフェーズで `stopPropagation()` まで行うよう修正した。

なお `Ctrl+Shift+I` については、`Ctrl+I`（= 0x09）が漏れる懸念があったため実際の入力経路で検証したが、xterm.js は `Ctrl` + `Shift` + 英字を制御文字に変換しないため問題なかった。

### 複数行貼り付けの確認ダイアログ

PowerShell + ConPTY はブラケットペーストに対応していないため、複数行を貼り付けると各行がそのまま実行される。事故を防ぐため、2行以上なら内容を見せて確認する。

- 末尾の改行1つは行数に数えない（「コマンド1行＋改行」は確認しない）
- 「今後表示しない」は**貼り付けを選んだ時だけ**反映する。キャンセルと同時に無効化されると、次回いきなり実行されて危ないため
- ブラケットペースト対応のシェルでは各行が実行されないので確認を省略する

### デバッグログ

DevTools で見えるのはレンダラー側の、しかも開いている間だけである。一方でこのアプリが壊れやすいのは起動時・終了時であり、その頃には DevTools を開く余地がない（前述の不具合9は、まさにログを入れたことで発覚した）。

- INFO 以上は常時、DEBUG は設定で切り替え
- 切り替えは右クリックメニューから。ログレベルは出力のたびに参照するので**再起動なしで反映される**。ただし起動時の処理はすでに終わっているため、その詳細は次回起動分から記録される。この差は分かりにくいので、有効化した時だけダイアログで案内する
- レンダラーの例外（`window.onerror` / `unhandledrejection`）も IPC で集約し、DevTools を開いていなくても残るようにした
- **PTY の入出力そのもの（打った内容・画面の中身）は記録しない。** パスワードを入力する場面があるため、DEBUG でもサイズや種別までにとどめる

## `start.bat` が動かない問題（2026-09-05・公開後）

公開後、`start.bat` が動作しないことが判明した。初版から LF 改行・UTF-8 で保存されていたことが原因で、次の二つが重なっていた。

- **改行が LF のみ** — cmd.exe は CRLF を前提とする。特に括弧で囲んだ複数行の `if` ブロックが壊れ、行の途中から実行される。再現時は `npm install に失敗しました。` が最初に表示され、その後 `'…見つかりません。初回のみ' is not recognized` などが並び、最後まで到達しなかった。
- **文字コードが UTF-8** — cmd.exe は `.bat` を**その時のコンソールのコードページ**で解釈する。このPCのシステム既定は CP932（`HKLM\...\Nls\CodePage\OEMCP`）なので、UTF-8 の日本語が誤ってデコードされる。

### 検討した案

| 案 | 結果 |
| --- | --- |
| CRLF + CP932 で保存 | CP932 環境では正常に動く。ただし UTF-8 コンソールの環境では同じ問題が起き、GitHub 上の表示も文字化けする |
| CRLF + UTF-8 のまま先頭に `chcp 65001` | **不安定なため不採用。** cmd.exe はファイル内の位置をバイト単位で追うため、コードページを途中で変えると位置がずれ、日本語の行が途中で分割されて実行される。`chcp` の前後どちらに日本語の `rem` を置いても、内容によって壊れたり壊れなかったりした |
| **CRLF + ASCII のみ（採用）** | どのコードページでも解釈が変わらない。GitHub上の表示も崩れない |

`.bat` は「その環境のコードページで解釈される」以上、非ASCIIを含めた時点で環境依存になる。ランチャーという性質上、確実に動くことを優先して**メッセージを英語にし、ASCII のみ**とした。日本語の説明は README と本ドキュメントが担う。

あわせて `.gitattributes` に `*.bat text eol=crlf` を追加した。リポジトリ内は LF で保持されるため、clone する人の `core.autocrlf` 設定次第では LF のまま取り出されて再発しうるからである。

修正後、コンソールのコードページを 932 と 65001 の両方に切り替えて `start.bat` を実行し、いずれもアプリが起動し解析エラーが出ないことを確認した。

## タブごとのClaude Codeの状態表示（2026-09-05）

「どのタブが確認待ちなのか、そのタブを開かずに分かるようにしたい」という要望から入れた機能。先行して作った [claude-signal-tray](https://github.com/Helicon1968/claude-signal-tray) はプロセスのI/O量から状態を推定しているが、同ドキュメントに記録があるとおり **CLI版の確認待ちは検知できない**（ローカル端末での入力待ちであり通信が発生しないため）。kanaterm は端末そのものなので、この制約が無い。

### 判定条件は実測してから決めた

パターンを憶測で書くと、原因の分からない誤判定に悩むことになる。先に**画面キャプチャの仕組みだけ**を入れて実データを集め、それから条件を決めた。採取した61件の画面（ツール実行の許可3・フォルダの信頼確認2・モデル選択2・AskUserQuestion2・claude未実行5・その他）で条件を検証している。

判定は次の順に評価する。**順序に意味がある。**

1. `Esc to cancel` があれば**確認待ち**
2. Claude Code のUI（`─`/`▔` の罫線、`⏵⏵`/`⏸`）が無ければ**未実行**
3. 直近700ms以内に出力があれば**作業中**
4. それ以外は**待機中**

### 実測して分かったこと

- **確認待ちは4種類とも同じフッターを出す。** ツール実行の許可・フォルダの信頼確認・モデル選択・AskUserQuestion のいずれも `Esc to cancel` を含む。1つの条件でまとめて拾える。
- **作業中はスピナーの字形で判定してはいけない。** 採取した61件のうち作業中はわずか2件だった。作業中はスピナーが再描画され続けて出力が途切れないため、「出力が止まったら記録する」キャプチャがほとんど走らなかったからである。裏を返せば **「画面が動き続けている」こと自体が作業中の証拠**であり、字形（`✻✽✳`）に依存しないぶん堅牢でもある。
- **確認待ちの判定はUIの有無より先に置く必要がある。** 実装当初はUIの有無を先に見ていたが、テストでモデル選択画面が「未実行(灰)」に落ちることが判明した。あの画面の罫線は `─` ではなく `▔` だったためである。確認待ちの取りこぼしはこの機能の目的そのものを損なう。
- **ちらつき対策は必須。** フォルダの信頼確認に答えた直後、1.75秒だけ素のシェルプロンプトに見える瞬間がある。そのまま反映すると灰が一瞬光る。同じ判定が一定回数続くまで表示に反映せず、特に灰へ落とすときは長めに構える。

### 見つかった不具合

実機で確認したところ、4タブすべてが灰のままだった。原因は `screenTail()` がバッファ末尾から数えていたことで、画面が縦に長く内容が上部だけの場合に空行しか読めない状態だった。キャプチャ（画面全体40行）では表面化せず、判定（末尾24行）で初めて露見した。「最後に文字がある行」まで戻ってから遡るよう修正した。

### 見送ったこと

- **claude-signal-tray への状態提供。** kanaterm が状態ファイルを書けば signal-tray のCLI検知の穴を埋められるが、signal-tray は Cowork など端末以外との連携も前提にした作りのため、いったん見送った。
- **OSC 133 によるシェル統合の拡張。** 当初は「コマンドが動いているか」を確定的に取るために必要と考えていたが、画面の内容だけで足りることが実測で分かったため不要になった。なお、既存の OSC 7 の到着時刻（プロンプト描画からの経過時間）も判定に使えるかを検討したが、**シェルのプロンプトで放置しているだけでも値が伸びる**ため使えなかった。

## 検証方法

GUI アプリのため、目視だけでは「直ったつもり」になりやすい（不具合9がその例）。以下の方法で機械的に確認した。

- **Chrome DevTools Protocol** — `--remote-debugging-port` で起動し、レンダラーへ接続して内部状態を直接読む。タブの並び、xterm のバッファ内容、`term.onData` に流れた実データ（＝ PTY へ送られた内容）を取得できるため、「何がシェルへ送られたか」をバイト単位で確認できる。
- **`Input.dispatchKeyEvent`** — 合成イベントでは `before-input-event` を通らないため、キー入力の検証には CDP の入力ディスパッチを使う。
- **Win32 API（P/Invoke）** — ネイティブのダイアログやコンテキストメニューは CDP から見えない。`EnumWindows` でウィンドウを列挙してタイトルを確認し、`SetForegroundWindow` + `SendKeys` で操作した。
- **純ロジックの単体チェック** — `store.js` の異常系（壊れた JSON、不正なタブ）、OSC 7 の URI 変換、貼り付けの行数判定、ログのレベルフィルタとローテーションは、Electron を起動せず Node で確認できる。

## 得られた知見

- **「直った」と判断する前に、再現手順そのものを疑う。** 不具合9は、遅延保存のタイマーがたまたま先に発火していたために「保存されている」ように見えていた。変更してから閉じるまでの時間を詰めて初めて再現した。
- **ログを入れると別の不具合が出てくる。** `close` イベントが発火していないことは、ログを仕込むまで誰も気づけなかった。
- **高DPI環境では座標の往復が保証されない。** 「書いた値がそのまま読める」を前提にした保存・復元は、拡大率次第で少しずつずれる。
- **`.ps1` の BOM は必須。** Windows PowerShell 5.1 は BOM が無いと日本語を化けさせ、コメントであっても構文エラーを起こしうる。
- **ログに何を書かないかを先に決める。** 端末アプリの入出力はパスワードを含みうるので、詳細ログの設計時点で対象外にした。
